# Declared response security policies

Workflow expectations, access-case proofs and authenticated browser session
controls can include `response_headers` and `response_cookies`. These evaluate
actual HTTP response metadata alongside existing body/status/state assertions.
They use declared application expectations; no policy is inferred from a generic
response and no request is generated by this module.

Example expectation on an explicitly supplied account endpoint:

```json
"expect": {
  "statuses": [200],
  "json_equals": {"/account_id": "authorized-test-owner"},
  "response_headers": {
    "Cache-Control": {"comma_tokens": ["no-store", "private"]},
    "X-Content-Type-Options": {"equals": "nosniff"},
    "Access-Control-Allow-Origin": {"present": false}
  },
  "response_cookies": {
    "session": {"secure": true, "httponly": true,
                "samesite": "Lax", "path": "/", "domain_absent": true}
  }
}
```

Use expectations appropriate to the application. This example is not a universal
security baseline: an endpoint may legitimately use CORS or different caching,
cookie paths, domain scopes or SameSite behavior. The cookie rule checks a cookie
issued by this response; an already stored browser cookie is not equivalent.

Header names are case-insensitive. `present` checks existence or absence;
`equals` requires exactly one value with case-sensitive exact equality;
`contains` requires every occurrence to contain the case-sensitive literal;
`comma_tokens` requires case-insensitive bare comma-list members. It understands
quoted commas and rejects unbalanced quotes/empty members. A directive with
an assigned value is not a bare token, so `private="field"` does not prove the
bare `private` requirement. This is not a full Cache-Control/CSP/CORS parser;
`contains` alone does not establish semantic policy enforcement. Absent-header
requirements cannot be combined with value assertions for that header.

Cookie names are case-sensitive. `secure`, `httponly` and `domain_absent` require
literal booleans; `samesite` requires `Lax`, `Strict` or `None`; `path` is exact.
Each named cookie must appear exactly once in duplicate-preserving Set-Cookie
metadata. Missing cookies, unparseable/combined Set-Cookie fields or multiple
same-name cookies fail the cookie assertions rather than guessing the effective
browser cookie across different paths/domains. This does not test cookie expiry,
prefix semantics, browser acceptance, session rotation, revocation or CSRF impact.

The HTTP transport retains separate header fields; the browser transport uses
the final main-document response's header array, not subresources or redirect
intermediate responses. Actions that navigate can therefore change which final
document is checked. Body assertions continue to use the selected rendered DOM
representation in browser mode. Cookie values and raw headers remain in memory;
persisted checks contain only header/cookie name, operator and pass/fail.

Mappings are bounded to 100 headers and 100 cookies, names to 128 characters,
literal strings to 4,096 characters and token lists to 100 items. Metadata
evaluation is bounded to 1,000 fields and 131,072 aggregate characters. Each
check records `evidence_complete`. Invalid/incomplete metadata, unsupported
collapsed value metadata, malformed comma lists and ambiguous cookie records
make the workflow/access observation inconclusive rather than producing an
invariant finding or a completed negative access check. Missing required headers
or cookies in complete metadata are ordinary policy mismatches. Programmatic custom transports must
supply `header_items` as a list of separate `(name, value)` pairs for value and
cookie checks; a collapsed `headers` dictionary supports only presence checks.

All existing workflow origin/scope/credential/session/budget checks still apply.
Failed workflow policy assertions remain invariant failures requiring impact
review; they are not automatically validated vulnerabilities. Access proofs
still require positive resource-specific body evidence and repeated allowed /
denied observations; headers alone cannot confirm an access violation.

This feature was reviewed statically only. No tests, browsers, applications,
scanners or assessments were run; behavior is unverified at runtime.
